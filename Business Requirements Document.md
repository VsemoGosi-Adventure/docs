# Бизнес-требования к приложению «Авантюра»

**Проект:** Сервис спонтанного поиска компании «здесь и сейчас»  
**Команда:** «ВсёМоГуси»  
**Документ:** Бизнес-требования (BRD), версия 2.0 (без ручной модерации)

---

## 1. Цель и ценность продукта

Предоставить пользователю возможность находить компанию для досуга **в течение нескольких минут**, минимизируя его усилия: система сама наполняет базу актуальными событиями через изолированный краулер и сама присылает релевантные уведомления о происходящем рядом. 

Пользователь полностью освобождён от роли организатора: события не требуют одобрения заявок или согласований с авторами.

**Ключевые ценности для пользователя:**
- **Нулевая организационная нагрузка:** пользователь не создаёт события и не ждёт подтверждений — находит готовое событие и присоединяется в один клик.
- **События и люди рядом:** гео-ранжирование с учётом текущего местоположения и персональных интересов.
- **Быстрый добор через «Пинг»:** любой участник на месте может позвать людей поблизости, если не хватает компании.
- **Безопасность (Анти-сталкинг):** встречи проходят исключительно в проверенных публичных городских локациях; точные координаты места и чат доступны только реальным участникам сбора.

## 2. Целевые пользователи

| Роль                       | Описание                       | Потребности / Возможности                                                                                                                                          |
| -------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Гость**                  | Неавторизованный посетитель    | Просмотр ознакомительной ленты (с примерными районами), регистрация и вход.                                                                                        |
| **Пользователь**           | Авторизованный участник        | Настройка интересов, просмотр гео-ленты, вступление в событие в 1 клик, выход из события, отправка «Пинга» на встрече, общение в чате, получение push-уведомлений. |
| **Краулер (Система)**      | Автономный воркер сбора данных | Автоматическое создание проверенных публичных локаций и событий на основе парсинга внешних афиш/площадок.                                                          |
| **Администратор** (Бэклог) | Внутренний персонал платформы  | Мониторинг воркеров краулера, системная модерация и отключение неактуальных внешних источников.                                                                    |

## 3. Функциональные требования

### 3.1 Аутентификация и профиль
- **BR-01.** Гость может зарегистрироваться (email + пароль) и авторизоваться в системе.
- **BR-02.** Пользователь может выйти из сессии; обновление сессии происходит по refresh-токену.
- **BR-03.** Пользователь может просматривать и редактировать профиль (имя, аватар, описание).
- **BR-04.** Пользователь может выбирать и менять персональные интересы из системного справочника (спорт, кофе, настольные игры и т.д.).

### 3.2 Гео-лента и поиск
- **BR-05.** Пользователь видит интерактивную карту и ранжированный список актуальных событий поблизости.
- **BR-06.** Выдача событий сортируется по физической дистанции (PostGIS) и степени совпадения с выбранными интересами профиля.
- **BR-07.** В общей ленте отображается **только примерный район** события без точного адреса и координат (механизм защиты от сталкинга).
- **BR-08.** Пользователь может фильтровать события по категориям и тегам интересов.

### 3.3 События (Встречи)
- **BR-09.** **Создание событий закреплено исключительно за Краулером.** Пользователи не могут создавать события вручную.
- **BR-10.** События формируются на базе проверенных публичных мест с атрибутами: название, описание, точный адрес, временное окно (начало/конец), теги интересов и лимит участников (`max_participants`).
- **BR-11.** **Модель входа — только Open:** Любой пользователь может присоединиться к событию в один клик при наличии свободных мест (`current_participants < max_participants`). Никаких закрытых заявок и ручной модерации.
- **BR-12.** Пользователь может в любой момент покинуть событие, освободив место для других участников.
- **BR-13.** Точный физический адрес, координаты локации и доступ к чату открываются **только после нажатия «Присоединиться»**.
- **BR-14.** Жизненный цикл события управляется автоматически по времени: событие переходит в статус `finished` по наступлении времени окончания (`ends_at`).

### 3.4 «Пинг рядом» (Киллер-фича)
- **BR-15.** Любой подтверждённый участник события при наличии свободных мест может отправить «Пинг» — локальный импульсный сигнал в заданном радиусе.
- **BR-16.** Пользователи с совпадающими интересами, находящиеся в радиусе охвата, получают push/WS-уведомление (*«В 300 м от вас собираются на настолки, осталось 2 места»*).
- **BR-17.** Сигнал «Пинг» имеет ограниченный срок жизни (TTL) и автоматически деактивируется по истечении времени.
- **BR-18.** «Пинг» **не является** новым событием, а служит инструментом оперативного добора людей на уже существующую встречу.

### 3.5 Чат события
- **BR-19.** Участники встречи могут вести переписку в групповом чате реального времени (WebSocket).
- **BR-20.** Доступ к чату предоставляется автоматически при вступлении в событие и блокируется при выходе из него.

### 3.6 Проактивные уведомления
- **BR-21.** Пользователь получает оповещения: о появлении новых событий поблизости от краулера, входящих «Пингах», напоминаниях о начале встречи и сообщениях в чатах.
- **BR-22.** Оповещения передаются через постоянное WebSocket-соединение (в активном приложении) и через push-каналы (в фоновом режиме).

### 3.7 Автонаполнение (Краулер)
- **BR-23.** Сервис сбора данных по расписанию парсит внешние открытые агрегаторы мероприятий и тематические площадки, формируя базу проверенных локаций и событий.
- **BR-24.** Краулер функционирует в изолированном контуре (Host 1) и передаёт спарсенные данные через брокер Redpanda, исключая риск бана IP основного сервера.

## 4. Нефункциональные требования

| Категория | Требование |
|---|---|
| **Платформы** | Клиентское приложение на базе React Native / Expo с поддержкой запуска в браузере (Web PWA) и на мобильных устройствах. |
| **Ресурсоёмкость** | Полный стек сервисов и инфраструктуры оптимизирован для стабильного запуска в Docker-окружении с лимитом **до 8 ГБ RAM**. |
| **Безопасность** | Stateless JWT-аутентификация с ротацией refresh-токенов; скрытие геолокации и приватных каналов от неавторизованных лиц; сетевая изоляция воркеров краулера. |
| **Производительность** | Пространственные выборки на базе PostGIS с GiST-индексацией со временем отклика до 1–2 секунд. |
| **Связность архитектуры** | Микросервисная организация бэкенда с использованием шины Redpanda для асинхронных процессов и логической изоляцией схем БД. |

---

## 5. Границы скоупа

- **В скоупе (MVP):** регистрация и аутентификация, профиль и интересы, гео-лента и карта (PostGIS), автоматическое создание событий краулером, мгновенное вступление (`open`) и выход, WebSocket-чат, push/WS-уведомления, отправка и получение «Пинга».
- **Вне скоупа (Бэклог):** функционал CheckIn (подтверждение физического присутствия по координатам).

---

## 6. Критерии приёмки

1. Пользователь успешно проходит регистрацию, задаёт интересы и видит на карте события, автоматически собранные краулером.
2. Пользователь не может создавать события вручную — они генерируются системой.
3. Пользователь присоединяется к открытому событию в один клик без ожидания модерации, после чего ему сразу открываются точные координаты и чат.
4. Участник встречи может отправить «Пинг», а находящиеся поблизости пользователи с соответствующими интересами получают оповещение.
5. Изолированный краулер наполняет базу без взаимной блокировки и перебоев в работе клиентского API.
